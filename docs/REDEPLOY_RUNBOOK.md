# Mainnet Vault Redeploy Runbook

This runbook moves CIRCLA from the live vault `0x25Fcc446bBfb7444F0b9738423dD58713361010d` to a new vault built from the invite-only contract (invite list, execution price floor, USDC withdrawal for every recipient).
Vaults are immutable, so the fixes only reach users through a new deployment and a repoint of the bot and the Mini App.

## Before you start

1. Merge PR #1 into `main`.
   The Mini App and bot already handle both vault versions, so merging before the deploy is safe.
2. Decide which wallet owns the new circle.
   The owner's Circle membership card only appears in the Mini App for the owner address.
   If the owner uses a different wallet in the app (for example a Coinbase Smart Wallet), set `CIRCLA_OWNER` to it in step 3, and the deploy hands ownership over in the same broadcast.
3. Fund the deployer with a little ETH on Base.
   The fork rehearsal used about 3.4M gas, roughly 0.00004 ETH at 0.0106 gwei.
4. Export `BASESCAN_API_KEY` in your shell for verification.
   Leave `DEPLOYER_PRIVATE_KEY` unset: the deploy script asks for it with hidden input, so it stays out of shell history and the process list.
5. Pick a weekday during US market hours for the smoke test in step 7.
   Over weekends the feed holds Friday's close, and the 5% execution price floor can reject trades.

## Steps

### 1. Close joining on the old vault now

This is independent of the redeploy and closes the open-join gap today.
From the owner wallet `0x62f5…8784`:

```bash
cast send 0x25Fcc446bBfb7444F0b9738423dD58713361010d "closeCircle()" --rpc-url base --interactive
```

Check that `circleOpen()` returns `false` afterwards.
A read-only simulation of this call from the owner succeeds.

### 2. Rehearse on a fork (rehearsed)

```bash
anvil --fork-url https://mainnet.base.org --chain-id 8453
```

In a second terminal, run the same script against the fork with an anvil test key (never the real one):

```bash
BASE_RPC_URL=http://127.0.0.1:8545 script/deploy-mainnet.sh
```

A fork run writes `broadcast/DeployMainnetVault.s.sol/8453/run-latest.json`, the same path a real mainnet run uses, and a record in `deployments/`.
Back up the broadcast folder before rehearsing and restore it afterwards, and delete the rehearsal record from `deployments/`.

On 2026-11-06 the script deployed on a fork with the defaults and with a custom name, two invites, and an ownership handoff.
It refused to send anything for a wrong chain, an invalid quorum, or any answer other than `DEPLOY`.

### 3. Deploy and verify on Base mainnet

Commit everything under `src/` and `script/` first; the script refuses to run with uncommitted changes there so the deployed bytecode matches a commit.
Set any settings that differ from the defaults, then run the script:

```bash
CIRCLA_INVITES=<WALLET_1>,<WALLET_2> CIRCLA_OWNER=<APP_WALLET> script/deploy-mainnet.sh
```

| Variable | Default | Meaning |
| --- | --- | --- |
| `CIRCLA_CIRCLE_NAME` | `Nairobi Tech Circle` | Name stored onchain |
| `CIRCLA_MAX_MEMBERS` | `5` | Seats |
| `CIRCLA_QUORUM` | `2` | Yes votes needed |
| `CIRCLA_CONTRIBUTION_TARGET` | `250000000` (250 USDC) | Stored target |
| `MAX_TRADE_AMOUNT` | `100000000` (100 USDC) | Per-proposal limit |
| `PROPOSAL_TTL` | `1800` | Seconds a proposal stays open |
| `CIRCLA_INVITES` | none | Comma-separated wallets invited at deploy |
| `CIRCLA_OWNER` | deployer | Final owner after invites are set |
| `BASE_RPC_URL` | `https://mainnet.base.org` | RPC; a dedicated endpoint is more reliable |

The script runs the unit tests, simulates the whole deploy against live Base state, and prints the deployer, balance, owner, settings, and invites.
It broadcasts only after you type `DEPLOY`, verifies on Basescan when `BASESCAN_API_KEY` is set, and writes `deployments/base-mainnet-vault-<timestamp>.json` with the vault address, deploy block, transactions, and commit.

Invite the owner's own wallet too, since the owner is not a member automatically.
`CIRCLA_OWNER` is a one-step transfer, so check the address in the simulation output before typing `DEPLOY`.

If verification did not finish, run it on its own:

```bash
forge verify-contract <NEW_VAULT> src/CirclaVault.sol:CirclaVault --chain base --watch \
  --constructor-args $(cast abi-encode "constructor(address,address,address,address,string,uint8,uint8,uint256,uint256,uint256)" \
  <DEPLOYER> 0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913 0xA433d976740203bAE030339e68d6f7b261aCEABd \
  0x8453000000000000000000000000000000000002 "Nairobi Tech Circle" 5 2 250000000 100000000 1800)
```

The constructor owner is always the deployer, because the deployer sets the invites before handing ownership over.

### 4. Invite more members later

Use the Mini App's Circle membership card from the owner wallet, or:

```bash
cast send <NEW_VAULT> "setInvites(address[],bool)" "[<WALLET_1>,<WALLET_2>]" true --rpc-url base --interactive
```

### 5. Repoint the code

Make one commit on a branch from `main` with the new address and deploy block in every row of the "What changes" table, except `circles.ts`.
The deploy script prints both values and saves them in the `deployments/` record.
Then run the checks that guard the repoint:

```bash
forge test
```

```bash
cd bot && npm test
```

```bash
cd web && npx tsc --noEmit && npm run build
```

Merge it to `main`.
Vercel rebuilds the Mini App and landing page, and Render rebuilds the bot because `autoDeploy` is on.

### 6. Update the bot on Render

1. Confirm `CIRCLA_VAULT_ADDRESS` on the Render service shows the new vault.
   A changed `value:` in `render.yaml` only applies after a blueprint sync, so set it in the dashboard if the sync does not run.
2. The service has no persistent disk, so each deploy re-seeds group bindings from `bot/seed/circles.json`.
   If a disk is ever added, delete `/app/data/circles.json` once so the new seed is copied.
3. In each bound group, run `/start_syndicate`.
   It should print the new vault address and restart the event watcher.
   Running it from a local checkout of the bot also regenerates `web/app/app/circles.ts` with the group title.

### 7. Smoke test on mainnet with small amounts

1. In a group, `/invite <uninvited wallet>` asks the owner to invite it; inviting it posts "was invited" in the group.
2. Two invited members join in the Mini App and deposit 1 USDC each.
3. One proposes a 1 USDC buy, both vote yes, and one executes.
   The bot posts each step, and `/status` shows the new pool value.
4. One member withdraws with Auto → USDC.
5. A wallet that was never invited cannot join (the app shows the invite-only state).

### 8. Wind down the old vault

1. The owner withdraws their share as raw stock, the only path the old contract allows for policy-cleared wallets:
   `cast send 0x25Fcc446bBfb7444F0b9738423dD58713361010d "withdraw(uint256,address)" 1000000000000000000 0x62f5a416c0077472822B3Ceb60bA2A6577D68784 --rpc-url base --interactive`.
   That sends 153,815 METAc to the owner and leaves the old vault empty.
2. Update the README to list the old vault as retired, keeping its transaction proofs as history.

## Announce to the group

> CIRCLA moved to a new, invite-only vault: <NEW_VAULT>.
> Send /invite <your wallet> here and the owner will add you, then open the app and tap Join circle.
> The old vault is closed to new members; your balance there is unchanged until you withdraw it.

## Rollback

The contracts cannot be changed, so rollback means pointing the bot and Mini App back at the old vault by reverting the step 5 commit.
The old vault stays usable for its existing members after `closeCircle()`; it only stops new joins.
If the new vault misbehaves, the owner can call `setSettlementPaused(true)` to stop proposal execution while withdrawals keep working.

## Risks to watch

- The deploy key controls invites, closing, and pausing on the new vault, so treat it like a treasury key.
- `VAULT_DEPLOY_BLOCK` must match the new deploy block, or `/members` scans the wrong range and reports wrong deposit totals.
- The 5% price floor can reject trades when pool prices drift from the Chainlink feed, most often over weekends.
